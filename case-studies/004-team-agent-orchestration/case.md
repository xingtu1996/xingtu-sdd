# Case 004 · Team Agent 编排机制

> **一句话**：给一批单角色 Agent 加一层 Team 抽象——不改任何现有角色，只加编排层，让「多角色怎么配合」从对话上下文里的一次性拼装，变成可沉淀、可传承的契约。
> **档位**：standard（架构设计档）｜ **状态**：方案已拍板、试点落地 ｜ **原 spec**：`specs/20260903-WB-A1-team-agent-orchestration/`（已脱敏：内部项目代号 → 「内部项目」）

## 一、背景问题（为什么做）

- 平台把 AI 专家分为「Agent 型（单个专业角色）」与「Team 型（多角色按协议协作）」。
- 内部项目有 19 个单角色 Agent，**无 Team 型**：多角色协作靠主 Agent 每次临时决定"叫谁、怎么配合"，会话结束即丢失，无法沉淀"这个场景的最优组合"。
- 核心痛点：①每次都要重新决定组合 ②协作模式存在对话上下文里、不可传承 ③没有「该场景最优搭配」的沉淀机制。

## 二、Spec 结构（怎么组织）

全量五件套（A1 为 P0 批次唯一项）：
```
00_README.md       # 一句话 + 背景动机 + SMART 目标 + 方案对比（含被否选项）
01_analysis.md     # 现状分析
02_requirements.md # 需求与验收
03_design.md       # 架构 + Team YAML Schema（活文档 <200 行）
04_tasks.md        # 任务分解
05_validator.md    # 验收判据
```

## 三、关键设计（怎么实现）

- **方案对比后拍板**：轻量 Team YAML（每 Team 一个 YAML：成员 + 协作协议 + 交付物契约 + 冲突仲裁）优于纯提示词层（无契约、不可传承）。
- **叠加不重构**：Team 层纯新增，不碰任何现有文件（除入口加一行路由指向）——现有单角色零改动是硬验收。
- **Team YAML 四要素 + 两可选**：成员 / 协作协议 / 交付物契约 / 冲突仲裁（+ 触发场景 / 验收标准）。
- **契约回流**：协作结果回流 `contracts/` + 变更日志，让「跑过的组合」变成可复用的资产。
- **试点先行**：先一个真实场景试点（如故障排查组合）跑通，再横向铺开。

## 四、验收结果（怎么算完成）

- G1：Team 层存在且原有单角色文件零改动 ✅
- G2：至少 1 个 Team 跑通真实场景 ✅（试点场景实测通过）
- G3：Team 契约可沉淀、可传承（协作结果回流契约目录）✅
- G4：与平台 Team 型抽象对齐（YAML 四要素可映射平台概念）✅

## 五、踩坑 → 规则反哺（复利点）

| 踩坑 | 反哺规则 |
|---|---|
| 多角色协作靠主 Agent 临时拼装 → 会话结束即丢 | 协作模式必须**契约化**：成员/协议/交付物/仲裁四要素沉淀 |
| 大改现有体系 → 回归成本爆炸 | **叠加不重构**：新抽象层纯新增，现有组件零改动作为验收项 |
| 方案 A/B 难取舍 | Spec 里先写**方案对比表（含被否选项与理由）**再拍板，被否选项留痕可复用 |
