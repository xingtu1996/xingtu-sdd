# Case 002 · 规则管家 rule-keeper

> **一句话**：规则体系 7 层载体、8 族 100 条编号全是「规则消费者」，缺一个「规则管理者」——用 lint/query/add 三个脚本让规则漂移从「靠人记住」变成「跑一下就红」。
> **档位**：heavy（架构级）｜ **状态**：✅ 已落地 ｜ **原 spec**：`specs/20260910-规则管家rule-keeper/`

## 一、背景问题（为什么做）

- 加一条规则要手动改 3-4 个文件（分册 / 速查 / 计数 / 变更日志），漏一处就漂移——编号已到 040，计数还停 37。
- 规则正文被复制成「第二份事实源」：Skill 内嵌整段规则正文，示例句被当模板扩散到 27 个文件。
- 事实源指针会分叉：约定「唯一事实源在 A 处」，但多个入口文档仍指旧的 B 处。
- 冻结口径只在文档里声明，无扫描拦截。
- AI 开工靠人判断读哪册规则，容易整目录全读浪费 token。

## 二、Spec 结构（怎么组织）

轻量 spec：只出 `00_设计说明.md` + execution-log（按 specs-engine 深度裁减，非内容稿不套全量五件套）。

## 三、关键设计（怎么实现）

- **SSoT 不动**：规则正文永远只在 `rules/RULES.d/`；管家**只抽取、检查、编排，绝不复制正文**——不制造第二份事实源（核心原则，不可违背）。
- **skill 管「何时用/怎么用」，脚本管「可执行」**：逻辑全在脚本，可独立跑、可被其他 Skill 调用。
- **三工具分工**：
  - `rule_lint.py`：六类体检（ID 双向闭环 / 计数一致 / 事实源指针 / 冻结口径扫描 / 手册状态声明 / 正文违规复制），P0/P1/P2 分级，有 P0 退出码=1（可挂门禁）。
  - `rule_query.py`：按任务类型实时从分册抽取最小规则集（写稿/选题/封面/发布/复盘/数据/品牌/变现），不复制正文。
  - `rule_add.py`：加规则一条龙（备份 → 写分册 ID 自增 → 回速查 → 同步计数 → 变更日志），默认 dry-run。
- **检查只读、修复另议**：自动修复只做无歧义项，有判断项交人。

## 四、验收结果（怎么算完成）

- ✅ 首次运行验收：必须扫出已知缺口（计数漂移 / 双指针 / 冻结叙事残留 / 老排版规范 / 正文内嵌）——**扫不出 = lint 无效，返工**。
- ✅ 六类检查全部落地，`--json/--md` 双输出，可挂改动闸门。

## 五、踩坑 → 规则反哺（复利点）

| 踩坑 | 反哺规则 |
|---|---|
| 规则一多就漂移，人工改多文件必漏 | 加规则走脚本四联动（rule_add），**默认 dry-run、备份先行** |
| 正文被复制成第二份 SSoT | 只引 ID 不复制正文；lint 检测「单文件 ≥6 个 ID 且含正文特征词」→ 提示改实时抽取 |
| lint 报告没人看 | 退出码化：有 P0=非零退出，**可挂门禁**（改动闸门/发布前） |

> 方法论关联：`specs-engine/references/core.md`（三铁律 / 流程纪律）· 引擎 `scripts/validator-check.sh`（静态门禁同款思路）。
