# Case 010 · 证据三目录：归档索引停在 V7，版本已经到 V13

> **一句话**：一次对客交付迭代 13 版、归档 25 份文件，归档索引却停在 V7、漏登 11 份——索引靠人手维护必然腐烂。本轮把「输入 / 由来 / 历史」三目录判据 + 机器对账门禁（V-6）+ 原子归档命令（`sdd.sh archive`）固化进引擎，索引从「自觉维护」变「门禁拦截」。
> **档位**：引擎特性反哺（实践 → specs-engine）｜ **时间**：2026-10-22｜ **出处**：对客交付实践蒸馏（客户与项目信息不收录）

## 一、现象

- 一次对外交付迭代到第 13 版，过程归档 25 份文件；`_archive/README` 索引停在 V7，**漏登 11 份**。
- 没有恶意、没有事故：每一版都「记得」更新索引，直到某次忙起来断了链——此后索引彻底失真，且无人发现。

## 二、根因

索引是**人手维护的缓存视图**，事实在文件系统里；两态之间没有机器对账，腐烂只是时间问题。这与引擎既有原则同源：execution-log 是状态事实源，00_README 状态行仅缓存视图——**缓存视图没人对账就必然漂移**。

## 三、引擎化（反哺 specs-engine 的全套，2026-10-22 落地）

| 件 | 内容 |
|----|------|
| `references/artifacts.md` | 三目录判据 + 权威排序：`_prompt/` 存输入（判据：「缺了这段就复现不出同一个结论」）、`_work/` 存过程（「是交付物的由来，不是交付物」）、`_archive/` 存历史（「曾经在 deliverables、现在不在」） |
| 三份 README 骨架 | `templates/_prompt.README.md` `_work.README.md` `_archive.README.md`；归档索引的「作废原因」列**必填** |
| `scaffold.sh --with-artifacts` | 长周期/多版本/对外交付才建三目录——**不为仪式感标配**（短平快 spec 零负担） |
| `validator-check.sh` **V-6** | 归档索引对账：机器查漏登，收口前必红 |
| `sdd.sh archive` | 移动 + 登记 + 记账原子完成，让人没有「忘了登记」的机会 |

## 四、效果

- 索引从「靠自觉」变「靠门禁」：漏登在收口前被 V-6 拦截，不再依赖事后发现。
- 三词诀：**输入（_prompt）/ 由来（_work）/ 历史（_archive）**——拿不准某份文件放哪，按这三个词对号入座。

## 五、踩坑 → 规则反哺（复利点）

| 踩坑 | 反哺规则 |
|------|---------|
| 索引靠人手维护 | **没有机器检查的索引必然腐烂** → 结构门禁 V-6 |
| 三目录想当标配推广 | 按需建：三判据不满足就不建，防「目录仪式感」反噬轻量档 |
| 归档只做 `mv` | 移动 + 登记 + 记账必须原子化（`sdd.sh archive`），拆开三步必漏一步 |

**可迁移**：任何「版本谱系要对外交代」的场景（交付/审阅/发布）都适用同一结构：事实在文件系统、视图靠机器对账、动作原子化。深一层的教训：**引擎的每次实战暴露的腐烂点，都应收敛为一条可执行的门禁**，而不是一条「下次注意」。
