# Case 006 · npm 包发布 SOP：把「踩坑式发布」变成「SOP 式发布」

> **一句话**：发包即标准化——把 npm 发布从「首次踩遍所有坑」变成「前置准备一次性、每次发布四步校验」的可复用流程，未来所有插件/工具/CLI 发布照此执行。
> **档位**：standard ｜ **状态**：✅ 已跑通（`dsh-xingtu-skills@0.1.0` 真实发布全流程沉淀）｜ **原 spec**：`specs/20260902-npm包发布SOP/`

## 一、背景问题（为什么做）

- npm 发布的坑高度集中在几处：**registry 镜像静默替换、2FA 新政策、tarball 内容体检、自动化环境登录态漂移**——首次发布的人会在每个坑上各踩一次。
- 发布是一次低频操作，靠记忆不可靠；坑位清单不沉淀，下一包发布重新踩。
- 目标：沉淀一份「前置准备（一次性）+ 发布前校验（每次必做）+ 发布 + 回滚」的 SOP，兼作内部教材。

## 二、Spec 结构（怎么组织）

```
00_README.md  # 一句话 + 前置准备表 + 发布前校验四步 + 发布 + 回滚 + 红线
```

（单文件 SOP 型 spec——流程文档，不需要拆多阶段。）

## 三、关键设计（怎么实现）

- **前置准备一次性**：npmjs 账号 + **2FA 必开**（新政策：bypass 2FA 的 token 限制账号变更、随后限制直接发布；不开 2FA 发布即 403）+ 恢复码只进密码管理器 Recovery Codes 字段，**严禁进文档/聊天/截图**。
- **每次发布四步校验**：
  1. `package.json` 版本语义化（0.1.0 / 0.2.0 / 1.0.0）
  2. `npm pack --dry-run` 看 tarball 文件清单是否干净（files 字段漏/多）
  3. `npm whoami --registry https://registry.npmjs.org` 确认登录态
  4. 插件类额外：`dsh-plugin-dev check` 静态校验
- **两个坑显式化**（写进 SOP 而非靠人记）：
  - 本机 registry 常是镜像源，发布必须显式 `--registry https://registry.npmjs.org`
  - 自动化环境 `NPM_CONFIG_USERCONFIG` 可能指向别的 `.npmrc` 读不到登录态 → 加 `--userconfig "$HOME/.npmrc"`

## 四、验收结果（怎么算完成）

- ✅ `dsh-xingtu-skills@0.1.0` 真实发布全流程跑通（前置 → 校验 → 发布），SOP 由实战沉淀而非理论编写。
- ✅ SOP 可直接复用为后续所有 npm 包（插件 / 工具 / CLI）的发布流程。

## 五、踩坑 → 规则反哺（复利点）

| 踩坑 | 反哺规则 |
|---|---|
| 镜像 registry 静默替换，发布进错源 | 发布命令**显式 `--registry`**，不依赖本机默认 |
| 2FA 新政策没跟上，发布被 403 | 发布类账号 2FA 必开，作为前置准备的硬项 |
| 恢复码进文档/聊天 = 凭证泄露风险 | 恢复码只进密码管理器 Recovery Codes 字段，台账铁律 SAF-003/011 |
| 自动化环境读不到登录态 | 显式 `--userconfig` 指定登录态文件，不赌环境变量 |
