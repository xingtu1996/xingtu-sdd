## 一、架构决策（最小集）

| 决策 | 选择 | 理由 |
|------|------|------|
| 合并方向 | **双向合并**：部署副本特性 → 主仓；主仓 privacy 修复 → 部署副本，收敛为三方一致 | 单向覆盖会丢一侧修复 |
| README.md 处理 | 手工合并（副本版 + 仓内 privacy 行），再回灌两份副本 | 唯一双侧都有独立改动的文件 |

## 三、Case 010 结构设计

`case-studies/010-artifact-trio-dirs/case.md`：现象（归档索引停 V7 / 实际 V13 / 漏登 11）→ 根因（索引靠人手维护、无机器对账）→ 引擎化（三目录判据 + V-6 + `sdd.sh archive`）→ 效果（门禁可拦截漏登）。脱敏：只保留量级数字（13 版本/25 归档文件/11 漏登），客户/项目/平台信息一律不写。文尾挂「踩坑→规则反哺」与引擎双向指链（案例库收录标准第 4 条）。

## 四、被否决方案

- **副本自动同步工具**（git hook / watch 脚本）：一次性欠账不该引入常驻机制；且 hook 在部分宿主不生效（工作区先例）。以纪律条目替代。
- **单向覆盖（仓→副本或副本→仓）**：必丢一侧修复，直接违背本 spec 动机。

## 五、风险

- GitHub push 仍不可达 → 本地 commit 收口，push 列入待办（不阻塞 spec 收口）。
- 009 原文若不存在 → 占位说明方案兜底，索引不再撒谎。
