***REMOVED******REMOVED*** 一、问题现状

- **现象**：`POST /orders` 偶发返回 500（约 1%），重试即成功；出错的订单状态卡「处理中」不再流转。
- **时间线**：2026-09-06 起灰度期出现；非 0 点峰值、无发布关联。
- **影响**：单量 ~200/日，卡单可人工补偿，无资损。

***REMOVED******REMOVED*** 二、根因分析

***REMOVED******REMOVED******REMOVED*** 直接原因

`OrderService.create()` 内同步调库存预留接口，连接池取连接超时抛 `TimeoutException` 未被捕获 → 500；订单已落库但状态推进事件未发 → 卡「处理中」。

代码引用：`src/main/java/app/order/OrderService.java:87`

***REMOVED******REMOVED******REMOVED*** 根本原因

库存调用超时配置偏紧（`rest-template.connect-timeout=1500ms`）且调用未做超时降级——设计缺陷（把同步依赖的失败等同于业务失败，且不留补偿路径）。

***REMOVED******REMOVED*** 三、影响面评估（必做）

| 影响维度 | 发现 | 风险等级 |
|---------|------|:---:|
| **下游调用方** | `create()` 被 `OrderController` + 异步补偿 worker 两处调用 | 中 |
| **异步消息消费者** | 状态推进靠发事件；本路径事件丢失即卡单 | 高 |
| **数据库变更** | 无 | — |
| **配置变更** | 超时/重试参数（YAML 两处，须单点） | 中 |
| **幂等机制影响** | 补偿 worker 重放需幂等键，已有 `idempotency_key` | 中 |

***REMOVED******REMOVED*** 四、方案对比

| 方案 | 改动范围 | 风险 | 推荐 |
|------|---------|------|:----:|
| A: 放大超时 + 加 try-catch 降级返回排队提示 | 2 处 YAML + Service 段 | 低，治标 | ✅ |
| B: 引入异步库存预留（本地表 + 定时扫补偿） | 中，动数据模型 | 高，需立项 | |

方案 A：超时放大到 3000ms + 捕获 `TimeoutException` 转业务态「排队中」，触发既有补偿重试链路（幂等兜底），不产生 500 与卡单。

***REMOVED******REMOVED*** 五、安全条件初判

| 条件 | 判断 |
|------|------|
| **退出条件** | 补偿重试 3 次仍失败 → 人工介入标记 |
| **幂等条件** | 补偿重放依赖 `idempotency_key`，重复执行不重复扣预留 |
| **回滚条件** | 纯配置+异常路径改动；异常时订单保持「处理中」可人工重置 |
