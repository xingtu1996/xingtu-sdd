# 子 Spec（Sub-Spec）—— 父管全局，子管切片

> 触发即读：**只在「父 Spec 下挂子 Spec」的场景读本文件**（拆不拆 / 怎么拆 / 父子链接 / 生命周期）。
> 不涉及子 Spec 的普通 Spec **不需要读**——这是把它从 core.md 拆出来的唯一理由（token 纪律）。
> 配套：`core.md`（三铁律/五阶段/文件规范）+ `orchestration.md §六`（子 Spec 并行）。

> **一句话**：父 Spec 管全局（架构 / 契约 / 共享清单 / 台账），子 Spec 管**一个可独立验收的切片**。
> 命名规范：`{父 Spec}/sub-specs/{YYYYMMDDHHMM}-{主题}/`。
> 章节号沿用 `10.x` —— 与 `core.md` / 模板 / 脚本里的交叉引用保持一致。

## 10.0 为什么有了 Spec 还需要子 Spec

这是本章最该先讲清的一问。**子 Spec 解决的不是「拆得不够小」，而是「拆了之后共享上下文要重复写 N 份」。**

### 三种拆法，代价不同

| 拆法 | 形态 | 共享上下文 | 冲突裁决 | 批次可见性 | 总收口 |
|------|------|-----------|---------|-----------|:--:|
| **不拆**（父里一节） | 一个 Spec | ✅ 天然一份 | ✅ 父自己 | — | — |
| **并列兄弟 Spec** | `specs/A`、`specs/B` | ❌ **各写一份** → 必然漂移 | ❌ **没有天然上级** | ❌ 靠人记「这几个是一批」 | ❌ 无总闸 |
| **子 Spec** | `specs/父/sub-specs/a` | ✅ **父持有一次，子只写差分** | ✅ **以父为准**（一句话定音） | ✅ 父一张索引表 | ✅ 父的 ✅ 看子 |

**推导**：一件事大到一鼓作气做不完 → 必须拆。拆成并列兄弟 spec，共享的架构 / 契约 / 枚举 / 台账每份都要重写一遍，N 份就是 N 个漂移源，而且**彼此冲突时没有裁判**。子 Spec 就是把「共享的那部分」上提到父，只让每个子写自己的差分。

> 一句话：**并列 Spec 拆掉的是共享性；子 Spec 保留了共享性，只切分工作量。**

### 那什么时候该用并列兄弟 Spec？

反过来，当「共享上下文本来就不多」时，硬套子 Spec 是过度设计。

| 问题 | 答「是」→ | 答「否」→ |
|------|:--:|:--:|
| 这件事**必须读懂父的约定**才能做吗？ | 子 Spec（继承父的上下文） | 往下问 |
| 它和父共享**同一批文件 / 契约 / 枚举 / 台账**吗？ | 子 Spec | 往下问 |
| 它做完了，**父的验收算不算完成了一部分**？ | 子 Spec | 往下问 |
| 三个都答「否」→ 只是**主题相关** | —— | **并列兄弟 Spec**（用「关联」字段互链即可） |

**实证对照**（同一项目里并存）：
- 子 Spec：父是「一个 API 大版本迁移」，11 个子各管一个接口 —— 共享双轨架构 / 开关表 / 台账，故必须继承
- 并列兄弟 Spec：父是「大会话方法论」，另一个是「会议归档」—— 主题相关但没有共享契约，各自独立

### 代价（诚实说）

子 Spec 不是免费：多一层目录、多一份索引要维护。**索引漂移是这个机制的真实故障模式** —— 实证中某项目父 README 的子 Spec 索引在 3 天内被修正 3 次（只列 1 个 vs 实有 6 / 7 / 10 个）。所以 10.8 有对应的机器对账门禁。**判据不满足就别拆，宁可不拆。**

## 10.0.1 业内对照：哪几条有背书，哪几条是我们有意偏离

> 调研时间 2026-10-09，来源见文末 §10.10。**分歧大于共识** —— 业内压根没有统一的「文档级父子」规范。

**✅ 业内有一手依据、已采纳的**：

| 结论 | 出处原文 |
|------|---------|
| 拆分的判据是「**独立可验收 / 独立状态 / 独立负责人 / 一次跑不完**」——**「大」本身不构成理由** | spec-kit: 每条 slice 必须 *"independently testable"*；唯一硬触发是 *"even a single phase is too large to handle in one run"* |
| 拆分是**最后手段**：*"Decomposition adds the most overhead of any strategy"* —— 先耗尽轻量手段再拆 | spec-kit 原文 |
| **稳定不可变 ID 作锚**：`ID` 列在被引用后不可改，它是可追溯锚点 | spec-kit: *"Keep the `ID` column immutable once a sub-spec references it"* |
| **双向指路**：子→父写引用行，父→子填路径单元格；且是 *"simple, greppable"* 的文本约定 | spec-kit |
| **父只定序不设计**：父是索引，设计留给子 | spec-kit roadmap 定义 |
| **「Roadmap first, then reconcile」**：先改父的索引条目，再动受影响的子 | spec-kit |
| **父不得先于子关闭** —— 且这条业内是**用机械手段挡**，不靠自觉 | Jira workflow validator（子未 Done 则父无法进 Done）+ automation 反向收敛 + 状态 rollup |
| 父的收口 = 子全 done + **索引状态回填** + 状态同步 | 同上 |
| **单源 vs 复制有明确分界**：稳定同源物单源引用；**易失外部物复制进来**，让 durable 记录独立可读 | mdd 项目明文：*"specs may not link out to research notes; anything a spec depends on is copied in so the durable record reads on its own"* |
| **过度拆分是真问题**，有一手复盘支撑 | InnoQ 一手自述：一个 story 膨胀到 **1070 行**，*"看起来像清晰，其实是组织良好的安全幻觉"*；Asana 三个月复盘出现 "spec review became a new blocker" / "documents no one owns" |

**⚠️ 我们有意偏离业内的两条（偏离要有理由，不是不知道）**：

| 维度 | 业内做法 | 我们的做法 | 为什么偏离 |
|------|---------|-----------|-----------|
| **父是什么** | spec-kit 的父是 **`roadmap.md` —— 纯索引，不是 spec**；共享物全部上提到**项目级 constitution** | 父是**完整 Spec**（自己的 analysis/requirements/design/validator + 共享上下文） | 我们的共享上下文（双轨架构 / 开关表 / 台账）是**这个主题独有**的，放进项目级 constitution 会污染全局；放在父里，作用域正好 |
| **子的自包含度** | 子**完全自包含**，不从父正文继承 | 子**继承父的架构 / 接口 / 契约**，只写差分 | 同理 —— 只要父持有共享上下文，子就必须继承它。**但代价要说清**：子不再能脱离父独立阅读，所以父指针是硬要求 |

> **这两条是同一个决定的两种表述**：我们把「共享上下文」放在**父**而不是**项目级**。选它的理由是作用域，不是省事。
> **诚实标注**：这也意味着我们比 spec-kit 多背一层继承耦合 —— 父改口径，子要跟。§10.6 的回流就是为这条设的。

**❌ 业内也明确警告、我们已有的**：按层拆（前端/后端）而非按切片拆 —— Shape Up 明确反对；把 spec 当**交接文档**而非**对话提示词** —— InnoQ 明确反对。

## 10.1 什么时候拆（四条判据，全中才拆）

| # | 判据 | 不满足的样子 |
|:--:|------|------|
| 1 | 是父的一个**可独立验收的切片** —— 有自己的 AC 与验证闭环 | 只是父的一个实现步骤 |
| 2 | 有**独立边界** —— 能圈死改哪些文件/范围，且写得出「不在范围内」 | 与同批其他项共享同一批文件 |
| 3 | 可**独立人审** —— 一次人审 = 一个子 Spec | 要连着别的项一起看才看得懂 |
| 4 | 与同批其他项**可并行或可独立排序** | 必须严格串行且强耦合 |

**典型场景**：大迁移逐项落地（一个接口 = 一个子 Spec）｜N 个同类小改造｜按批次推进的系列工作。

**不该拆**（反模式）：
- 父里一节就写得下的 —— 拆了只增索引维护成本（**实证**：某项目父 README 的子 Spec 索引漂移，在 3 天内被修正 3 次：只列 1 个 vs 实有 6 / 7 / 10 个）
- 跨多项的架构改造 —— 那本来就是**父**该干的事
- 纯 Bug 修复 / 配置调整 —— 走轻量档，别套子 Spec

> 产物上有个自检：子 Spec 的 `00_README` 有「**为什么单独立子 Spec**」一节。**写不出这节 → 本就不该拆。**

### 不拆的护栏（拆分是最后手段）

spec-kit 原话：**"Decomposition adds the most overhead of any strategy"**。拆之前先把轻量手段用尽：

```
① 限制每次执行的任务数          ② 拆成执行体（并行/委派）        ③ 还装不下 → 才拆子 Spec
```

**可观测的危险信号**（命中就该停下来重新议定粒度，而不是继续拆）：
- 单个 spec / 子 spec 逼近 **1000 行 Markdown**（实证：InnoQ 一个 story 膨胀到 1070 行，读起来像"组织良好的安全幻觉"）
- 出现「**spec 评审变成新的瓶颈**」或「**没人认领的文档**」
- 拆出来的子项**彼此不独立**（改 A 必改 B）—— 那是没切干净，不是在切

> 反过来也成立：spec 是**对话的提示词，不是交接文档**。写得越厚，团队越容易当成"已经交接完了"而停止讨论真正要建的东西（InnoQ 原话：*"Shared documents are not shared understanding"*）。

#### 切片怎么切：竖直贯通，不是按层横切

**一条切片要窄，但要贯穿所有层** —— 从数据到界面到测试走一条完整通路。**不要**「先把后端做完、再做前端、最后补测试」这样横切。

| ✅ 竖直切片 | ❌ 水平切片 |
|---|---|
| 一个接口：DDL → Mapper → Service → Controller → 用例 → 验证 | 「把所有 DDL 先做完」「把所有 Controller 先写完」 |

四条（取自 Matt Pocock 的 `to-tickets`，与 Shape Up「反对按层拆」同源）：

1. 每条切一条**窄但完整**的通路（schema / API / UI / tests 都切到）
2. 每条**自己就能演示或验证**
3. 每条体量 = **一个新鲜上下文窗口装得下** —— 这比「大不大」是更准的尺子（实证：某 spec 目录本身撑爆过上下文，`execution-log.md` 单文件 159.9 KB）
4. **预重构（prefactor）排最前** —— *"Make the change easy, then make the easy change."*

#### 例外：宽重构（wide refactor）不能硬塞进竖直切片

一次机械改动（改列名、改共享符号的类型）的爆炸半径横跨整个代码库，单个改动就打断上千个调用点 —— **没有哪条竖切能保持绿的**。这时改按 **expand–contract** 排：

```
① expand   新旧两种形态并存，谁都不破
      ↓
② migrate  分批把调用点迁过去（按包 / 按目录分批，每批一条切片）
           旧形态还在 → 批与批之间保持绿
      ↓
③ contract 确认零调用方后删掉旧形态（这条依赖所有 migrate 批）
```

> 连分批都保不住绿时：**保留这个顺序**，让它们共用一个集成分支，最后加一条「集成并验证」收口 —— **绿只在那一处承诺**。

#### 拆完要跟人对齐粒度（人审门禁，不可跳）

拆法是 AI 出的，**AI 不给自己当裁判**（同 SKILL.md 的深度定档铁律）。把清单摆给人看，逐条给三样：

| 给什么 | 内容 |
|---|---|
| **标题** | 一句话说清这条做什么 |
| **依赖边** | 哪几条必须先完成（`blocked by`）；无依赖的写「可立即开始」 |
| **交付什么** | 这条做完，**端到端**能跑通什么（不是「改了哪几个文件」） |

然后问三问：

1. **粒度对不对？**（太粗 / 太细）
2. **依赖边对不对？** —— 每条是否**只依赖真正卡住它的**那条。**多写了会假串行，少写了会并行踩踏**
3. **有没有该合并的、该再拆的？**

**人来拍板，迭代到人认可再落盘。** 落盘后从**前沿**（frontier = 依赖全部 ✅ 的那些）开始做。

## 10.2 目录与命名

```
{父 Spec}/                                  # 与普通 Spec 同构
├── 00_README.md … 05_validator.md
├── laws.md / execution-log.md              # ← 子不建这两份，见 10.3
└── sub-specs/                              # 目录名固定：复数 + 连字符
    ├── {YYYYMMDDHHMM}-{子主题}/
    └── {YYYYMMDDHHMM}-{tool}-{子主题}/      # 多 agent 同空间时带 tool 标
```

- 目录名固定 **`sub-specs/`**；存量项目的 `subspecs/`（无连字符）**兼容读取，不追溯改名**
- 子目录命名同父规则（时间戳前缀 + 可选 tool 标 + 主题），`Ticket` 段可省
- 存量的 `{YYYYMMDD}-{TICKET}-{主题}` 写法兼容（时间戳是其前缀）

## 10.3 文件骨架：子不建什么

| 文件 | 建？ | 说明 |
|------|:--:|------|
| `00_README.md` | ✅ | 子 Spec 导航：父指针 + **为什么单独立** + 范围表（含「不在范围内」）+ 复用资产 + 断点 |
| `01~05_*.md` | ✅ | 同父的五阶段；**深度裁减同样适用**（轻量档只留 01 + 05，实证有 2 文件子 Spec） |
| `06_测试记录.md` | 按需 | 执行实录（验证轮次多时建，单轮可省）；命名可随内容 |
| `laws.md` | ❌ | **继承父的** —— 子不重复定义方法论快照 |
| `execution-log.md` | ❌ | **执行事件记父的** —— 子不另立事实源 |

> **为什么子不建后两份**：父已经定义过一遍了。同一个概念存两处 = 必然漂移。
> 这叫 **共享物只引用不重定义** —— 与 10.5 是同一条原则。

### 「只引用」与「复制进来」的分界（别搞混）

「不重定义」不等于「一律外链」。业内有一条清晰的分界，**分错了两边都会出事**：

| 对象 | 做法 | 为什么 |
|------|------|--------|
| **稳定同源物** —— 枚举 / 常量 / 契约 / 术语 / 开关表 | **单源引用**，绝不复制 | 它们本来就该只有一份；复制 = N 个漂移源（实证：某项目一个规格变更要改 6 处 → 结果**一处都没改**，静默漂移了 5 个月） |
| **易失外部物** —— 会议纪要 / 调研笔记 / 客户原件 / 截图 | **复制进来**（或至少留一份快照） | 这些是"会消失"的 —— 外链一旦失效，durable 记录就读不通了（arc42 的 war story：外部系统文档托管在网络盘，生产故障当天正好不可用） |
| **关键 / 高风险接口** | 默认引用，**例外可复制片段** | 同上，权衡的是"挂了会不会读不通" |
| **代码** | **单向**：spec 指向代码，代码不回指 spec | 双向引用会让重构处处受限 |

> 判据一句话：**这个东西一个月后还长得一样吗？** 一样 → 引用；可能变/可能消失 → 抄进来。

## 10.4 父子双向链表（缺一即为断链）

父子关系靠**两条独立的指针**互指，任一缺失就是断链。加上**稳定 ID** 作锚。

### 父 → 子：父 README 的「子 Spec」索引表

```markdown
## 子 Spec（Sub-Spec）

> 本 Spec 为主，子继承之；**冲突以本 Spec 为准**。

| ID | 子 Spec | 目标（Intent） | 边界 | 依赖 | 状态 | 路径 |
|:--:|------|------|------|------|:--:|------|
| S1 | `asc.sync.list` 适配 | 某内部中台网关侧换实现，rock 零改动 | 不含 audit.send | — | ✅ | [`sub-specs/…`](./sub-specs/…) |
| S2 | … | … | … | **S1** | 🔵 | … |
```

- **ID 列**：`S1 / S2 / …`（或项目票号）。**一旦被某个子引用即不可变** —— 它是可追溯锚点，改了所有引用就断了（spec-kit 原话：*"Keep the `ID` column immutable once a sub-spec references it"*）
- **依赖列**：写依赖的 ID。**只启动依赖已 ✅ 的条目**；无依赖的可任意顺序（= 可并行）
- **边界列**：一行说清「不做什么」，防中途被邻项拖走

### 子 → 父：子 00_README 头部

```markdown
> **父 Spec**：../../00_README.md｜**父条目**：S2（继承 …；冲突以父为准）
```

> **父条目 ID 必须回写** —— 只有路径没有 ID，从子出发就只能"跳过去自己找"；有 ID 才能一眼定位它在父里的位置与兄弟。

> 父索引表用 `scaffold.sh sub` 自动建 + 自动加行，不用手写。表头若为旧的三列（子 Spec / 目标 / 状态）可保留，新表统一用七列。

### 「Roadmap first, then reconcile」

**先改父的索引条目，再动受影响的子**。父的索引表是"这件事怎么切分的"的**真相源**，不是事后补的账单。

## 10.5 继承与冲突裁决

- 子继承父的**架构 / 接口 / 契约 / 台账 / 执行点约定**，只在自身范围内派生
- **冲突以父为准** —— 这条要写进子 `00_README` 头部，让接手的 agent 不需要猜
- **共享物收敛在父或项目级**：新增枚举 / 常量表 / 日志关键字 / 开关表 / 契约 —— 子只引用不重定义
- 跨仓重复定义（两个独立仓各持一份）→ 两侧类注释写明同步义务 + 配**机器校验单测**（断言两处集合相等）

## 10.6 回流（子 → 父）

按 **Reverse Sync**（先改文档再改代码）执行，结论回流到四处：

```
① 子 Spec 变更日志
② 父 Spec 对应节 / 台账          ← 常漏
③ 父 README 子 Spec 索引行状态   ← 常漏
④ 若推翻了既有规则 → 反哺规则本身
```

> ②③ 是这条链最容易断的两环 —— 10.8 的门禁专为它们设。

## 10.7 人审粒度与并行

- **一个子 Spec = 一次人审** —— 粒度对齐人的 review 带宽
- 子 Spec 是**天然的并行单元**（父管全局、子管单项，范围天然不重叠）→ 机制见 [orchestration.md §六](./orchestration.md)
- **前提**：父的共享物（契约 / 枚举 / 日志关键字 / 索引表）先冻结，子才能解耦并行
- worktree 粒度与子 Spec 粒度对齐：**一个子 Spec = 一个批次 = 一个工作树**

## 10.8 门禁

```
□ 父 README 的子 Spec 索引行数 == sub-specs/ 下实有子目录数   ← validator-check.sh 自动对账
□ 每个子 00_README 有「> 父 Spec：」指针行 + 回写了父条目 ID
□ 父索引表的 ID 唯一；且被引用过的 ID 未被改动
□ 子 00_README 有「为什么单独立子 Spec」一节
□ 子 00_README 的范围表里「不在范围内」栏非空
□ 共享物没有被子在本地重定义（枚举 / 常量 / 日志关键字 / 契约）
□ 易失外部物（会议 / 调研 / 客户原件）已复制进来，没有裸外链
□ **父置 ✅ 的前提：所有子 Spec 已收口** —— 这条业内用机器挡（Jira validator），我们不靠自觉
□ 子收口时四处回流已完成（10.6）
```

`scripts/validator-check.sh` 已内置第 1、2 条（仅当本 Spec 含 `sub-specs/` 时触发，对普通 Spec 零开销）。

## 10.9 生命周期：父的 ✅ 前置

```
子：⬜ → 🔵 → ✅（各自的 AC 对账 + 变更日志）
                     ↓ 回填
父：索引行状态 ← 子完成后回填（只回填索引行，不回填父正文）
                     ↓
父的 ✅ = 本 Spec 自身收口  ∧  所有子 Spec 均已 ✅
```

**父不得先于子关闭。** 这条业内是用**机械手段**挡的（Jira workflow validator：子项未 Done 时父**无法**进入 Done；+ automation 反向收敛），因为靠自觉必然漏。

> 超大的子切片可以再下一层（子自己也建 `sub-specs/`），但 spec-kit 提醒：*"recursion adds overhead, so only go as deep as the context problem actually requires"* —— **按上下文需要定深度，别按对称性定。**
