# Specs 并行编排 — 多 Spec / 单 Spec 任务级并行（仅并行场景读）

> 何时触发：2+ 独立 Spec 并行、单 Spec 跨模块拆分、跨服务/跨仓侦查。单个串行任务不读本文件。

## 一、多 Spec 并行（契约优先）

```
Step 1: 构建依赖 DAG（检索 3 跳调用链/共享表/共享文件）
Step 2: 分类 → 串行组（有依赖）vs 并行组（完全独立）
Step 3: 跨单元握手协议先定死（provider 签名 + consumer 幂等 + 降级）→ 契约目录
Step 4: 独立组全并行推进（契约定了就能解耦）
```

| 依赖类型 | 策略 |
|---------|------|
| 接口依赖（A 调 B） | 先定契约 → 并行开发 |
| 数据依赖（共享表/字段） | 先改 schema → 并行 |
| 完全独立 | **并行** |
| 同文件改动 | **串行**（防 merge conflict） |

契约变更 → 更新契约目录 + 变更日志，让并行组读日志自适配，不靠人肉同步。

## 二、单 Spec 内任务级并行决策

定位：多 Spec 并行的下钻——**单个 Spec 内部**任务是否可并行、选哪种形态。
产出：01_analysis 并行性分析表 + 04_tasks 用 `∥` 标注可并行 Phase。

```
① 复杂度: 单文件/<20行 → 串行 ｜ 2-5 文件/1-2 模块 → 单执行单元 ｜ 跨 3+ 模块/大改 → 并行评估
② 拆分:   按模块/文件/Phase 拆 N 单元
③ 依赖:   强制 → 串行或 pipeline（拓扑序）｜ 选择/直接 → 契约化后并行 ｜ 无依赖 → 全并行
④ 形态:   见下速查表（以所用 agent 生态能力为准，不引外部编排工具）
```

## 三、优先级分级与「何时不并行」裁决（并行前必分）

> 并行提升吞吐，但会把**质量风险平摊给多个上下文**。开并行前先给每个任务定级，够格才并行——补自成熟工程体系的编排方法论（剥离业务专属示例）。

| 级 | 特征 | 策略 |
|----|------|------|
| **P0** | 核心链路 / 安全 / 计费·数据主链 / 不可逆 / 高耦合改动 | **串行保质量** + 对抗审查 + 人审，**不进并行** |
| **P1** | 独立功能 / 调研 / 文档 / 低风险重构 | **可并行**（Subagent ×N，无依赖、文件冲突 = ∅），上限 3-5 |
| **P2** | 低价值 / 可延迟（格式、清理） | 延迟或跳过，别占并行带宽 |

**规则**：P0 一律串行；P1 并行 ≤3-5（对齐人的 review 带宽，一次并行 Spec ≤3）；P2 顺延。文件冲突验证（交集 = ∅）在**派发前**完成，非事后补救。

**「何时不并行」裁决清单**（命中任一 → 结论写「串行」，不强行拆）：
- N=1 且单文件小改动（< 20 行）——并行编排开销 > 收益
- 有强制依赖（接口 / 数据 / 同文件）且契约未定死——先定契约或先改 schema，否则串行
- **P0 级高风险任务**——并行会把单点错误扩散成多点
- 无并行价值——"并行是手段不是目的"，为拆而拆反增协调成本

## 四、形态速查表

| 场景 | 形态 | 容器/单元 |
|------|------|:---:|
| 1-2 模块，独立子任务 | 容器内 parallel 子执行体 × N | 容器=工作流，单元=子执行体 |
| 有依赖子任务（拓扑序） | 容器内 pipeline 子执行体 | 容器=工作流 |
| 单 Spec 跨 3+ 模块 | 并行按模块 | 容器=工作流 |
| 2+ 独立 Spec | 多组并行工作流 | 容器=多条工作流 |
| 跨模块/跨服务排查 | 多执行体蜂群（不经容器） | 直接并行 |
| 文件冲突不可避免 | 串行 | — |

## 五、质量门禁

- **先过 §三 优先级分级**：P0 不进并行，够格才拆
- 并行声明须过**文件冲突验证**（各单元修改清单交集 = ∅）才可执行
- 并发上限 ≤ 编排工具默认（建议 3-5，勿盲目开满）
- **无并行价值时结论写「串行」，不强制并行**（并行是手段不是目的）
- 跨 Spec 并行升级走 §一 契约优先

## 六、子 Spec 并行（`sub-specs/` 下）

子 Spec 是**天然的并行单元**——父管全局（架构/契约/开关表/台账），子管单项，范围天然不重叠。机制见 [subspec.md](./subspec.md)。

### 并行前提：父的共享物先冻结

| 先定死 | 位置 | 为什么 |
|---|---|---|
| 架构与接口约定 | 父 `03_design` | 子只派生不重定义 |
| 枚举 / 常量 / 日志关键字 | 父或项目级资产 | 两个子各自定义 = 必然漂移 |
| 契约（provider 签名 / consumer 幂等 / 降级） | 父 `02_requirements` §安全三条件 | 契约定了子才能解耦并行 |
| 子 Spec 清单（谁做什么） | 父 README 子 Spec 索引表 | 防重复覆盖 |

> 父的共享物没冻 → 子并行 = 各写各的，合流时对不上。**先冻结，后并行。**

### 粒度对齐（可观测性最好）

```
一个子 Spec = 一个批次 = 一个工作树（worktree）   ← 三者一一对应
```

- worktree 的粒度应与**子 Spec 粒度对齐**（详见 `worktree-parallel` skill §六）
- 子 Spec 的批次 = 一次人审（见 subspec.md §10.7「人审粒度」）

### 子 Spec 并行的裁决

- 仍受 §三 分级约束：**父的核心链路（P0）不因拆了子就变可并行**
- 并行上限：一次跑 **≤3-5 个子 Spec**（对齐人的 review 带宽）
- 子之间**文件冲突验证**照旧（同一文件被两个子改 → 串行）
- 子 Spec 的 AC 写成**可执行命令**（grep 计数 / 断言未改 / 集合相等）→ 各执行体自证，主线程只抽验

### 回流（子 → 父）

子执行中发现的缺漏，按 **Reverse Sync** 先改文档再改代码，并回流到：
① 子 Spec 变更日志 ② **父 Spec 对应节 / 台账** ③ 父 README 子 Spec 索引行状态 ④ 若推翻既有规则 → 反哺规则本身

> ②③ 最容易漏 —— `validator-check.sh` 的子 Spec 索引对账就是为这条设的门禁。

## 七、worktree 真实并行（v2 新增）

纸面 DAG 标注 ∥ 不够，真多 agent 并行需要 git 隔离：

```bash
# 主会话在主线 spec 目录里，给某 phase 开隔离 worktree
bash scripts/sdd.sh start <phase> --worktree
#   → git worktree add ../.worktrees/<spec>-<phase> -b sdd/<spec>/<phase>
#   → 子 agent 在该 worktree 内跑，互不踩主线

# 子 agent 完成、主会话磁盘验收后，合并回主线
bash scripts/sdd.sh merge <spec>-<phase>
#   → 合并前人工核对三项：未提交/共改冲突/磁盘产物
```

- **契约目录先行**：跨并行单元的接口/数据依赖，先定死契约（provider 签名 + consumer 幂等），再开 worktree。
- **共改文件互斥**：两个 worktree 改同一文件 = 串行，不开并行。
- **验收认磁盘**：合并前主会话对 worktree 产物实跑/grep，不轻信子 agent 自述。
- 无 git 仓时 `start` 退化为非 worktree 模式（主线直接推进），不硬依赖。
