# Specs 核心方法论 — 铁律 + 五阶段 + 文件规范（触发即读）

> 配套：SKILL.md（触发/深度裁减 SSOT）+ orchestration.md（仅并行场景读）。本文件含铁律定稿。
> 术语：**项目宪法** = 项目专属护栏/红线（企业/团队自己的规则文件），与本文方法论铁律并行。

## 〇、铁律（方法论定稿）

### 三条铁律

| # | 铁律 | 含义 |
|---|------|------|
| 1 | **No Spec, No Code** | 方案未文档化不写实现代码。新功能需 analysis+requirements+design≥2 份；Bug 修需 analysis(根因+方案)；配置改需 requirements(AC+影响) |
| 2 | **Spec is Truth** | 文档与代码冲突，代码是 Bug，改代码。验收以 AC 为准、设计以 design.md 为准 |
| 3 | **Reverse Sync** | 发现 Bug → 先补文档漏洞（analysis 根因 / requirements 漏 AC / validator 回归用例），再改代码 |

### Spec × Plan 双保障

- Spec 文档 = 静态真相源；Plan Mode = 动态执行上下文。需求模糊先 Plan 澄清（人审），方向定了才落 Spec。
- Plan 执行中发现 Spec 遗漏 → 先改 Spec 再继续（铁律 3）。

### 流程纪律

| # | 纪律 |
|---|------|
| 1 | AC 必须可测试：每条标验证方式（curl / SQL / Both / 单元） |
| 2 | 安全三条件（退出/幂等/回滚）——涉及计费/库存/权限/写操作时 requirements 必填 |
| 3 | ✅ 三前置：00_README 复盘段非空 + 代码类 spec 对账节非空 + 澄清状态已显式记录；缺一保持 🔵 |
| 4 | execution-log 同步落账（append-only，状态事实源，禁事后回填）；**轻量档**不单独建文件，执行日志并入 00_README 复盘段 |
| 5 | 时间戳精确到分，用 `date "+%Y-%m-%d %H:%M"` 获取，**禁止编时间** |
| 6 | 完成后更新 specs 索引状态为 ✅ |

### 深度定档铁律

AI 按复杂度建议深度（轻量/标准/重量），**人确认后执行**——AI 不给自己当裁判。

## 一、五阶段工作流

```
影响分析(改哪/下游谁) → [01_analysis 问题分析] → [02_requirements 需求规格]
  → [03_design 详细设计] → [04_tasks 任务清单] → Code → [05_validator 运行时验证] → ✅
                                    ▲                                  │
                                    └────────── 反馈闭环（修复沉淀）─────────┘
```

每阶段产出即下阶段输入（derive→detail→plan），代码是 05 验证驱动的执行产物。

## 二、何时启动 Spec

**强制**：功能开发 / Bug 修复 / 技术改造 / 接口变更 / 数据模型变更 / 跨模块修改。
**可选**：调研类、文档类、纯配置（走轻量档）。
**快速判断**：改动会碰代码 + 有可验收行为 → 走 spec；纯阅读/临时脚本 → 不强制。

## 三、目录与命名

```
{specs父目录}/                              # 通常 .claude/specs，scaffold 自动建
├── README.md                              # Spec 索引（全部 spec 状态一览，scaffold 自动加行）
└── {YYYYMMDDHHMM}-{tool}-{Ticket}-{domain}/  # 一个 Spec 一个目录（tool/Ticket 可省）
    ├── 00_README.md / laws.md / 01_analysis.md ... 05_validator.md / execution-log.md
```

**目录命名** `{YYYYMMDDHHMM}-{tool}-{Ticket}-{domain}`：

> **为什么时间戳在最前**（这不是洁癖，是可发现性）：用户靠 IDE 的文件树按名排序找 spec。原话：
> > 「文件名称也更新一下，**确保我能够通过 idea 的排序及时找到这个 specs 文件夹**」
> 所以时间戳必须是**前缀**，否则排序失效。改名时要保住这个性质。

- `YYYYMMDDHHMM` 创建日期**精确到分**（前缀，按时间排序即定位；旧 `YYYYMMDDHH` 是其前缀，按小时截取的排序仍兼容）。
- `tool` 工具/agent 标（取 `$XINGTU_TOOL` 或 `scaffold --tool`，如 `qwenwork`/`doubao`/`workbuddy`/`zcode`/`cli`）——**解决多 agent 共用同一空间时 spec 无法区分谁开的、无法按 agent 过滤**；省 `Ticket` 时为 `{YYYYMMDDHHMM}-{tool}-{domain}`。
- `Ticket` 项目编号（有则加，如 `TICKET-123`）；`domain` 业务域简述（kebab-case）。
- 全可省到 `{YYYYMMDDHHMM}-{domain}`；撞名（同分钟同工具同名）scaffold 自动追加秒位兜底、不再硬失败，保并行不丢件。

**生命周期**：⬜ 待启动 → 🔵 进行中 → ✅ 完成（tasks 全勾 + 代码提交 + ✅ 三前置）。

## 四、深度裁减

| 档 | 必填（scaffold 一律落盘全骨架，深度只约束"填哪些"） |
|:---:|------|
| 轻量 | 01_analysis + 05_validator（单文件 Bug/配置） |
| 标准 | 01_analysis ~ 05_validator 全五 + execution-log（功能开发/跨模块，默认） |
| 重量 | 同标准 + 方案对比 + 暂停点（架构改造/计费·库存·权限） |

> 完整档位表在 SKILL.md（唯一 SSOT）。骨架文件未选为必填的留空或整文件删除均可（轻量档 02/03/04 可删）。

## 五、新建 Spec 流程

```
0. 方向未定 → 先澄清（人审），定了才落盘
1. scaffold new 建骨架（README 索引行已自动加，无需手加）
2. 01_analysis ← 现状+根因+方案对比+影响面
3. 02_requirements ← 可测试 AC + 安全三条件（涉及计费/库存/权限）
4. 03_design ← 架构决策 + 接口/数据流/结构变更 + 测试场景标注
5. 04_tasks ← 任务 + ∥ 并行标注
6. 05_validator ← 从 AC 派生验证用例
7. 开工首条：execution-log 记澄清状态；信息不全先问后建
```

## 六、各文件编写规范

### 01_analysis.md
问题现状（时间/单号/截图 + 影响范围）→ 根因分析（直接：`文件:行` 引用 / 根本：设计缺陷·边界·并发）→ 方案对比（表格：改动范围|风险|推荐）→ 影响面评估（下游调用方/消息消费者/DB/配置/入口/幂等/事务，按技术栈裁剪，无对应物删行）→ 安全条件初判。

### 02_requirements.md
用户故事（作为{角色}要{功能}以便{价值}）→ **验收标准表**（#|标准|验证方式 curl/SQL/Both/单元|优先级，≥1 条 P0）→ 影响范围 → 非功能（性能/兼容/幂等）→ **安全三条件**（退出/幂等/回滚，不可省略）。契约变更附扩展节（API/消息/数据模型/监控）。

### 03_design.md
架构决策（同步异步/事务/降级）→ 影响面确认（所有波及文件/消息路线）→ 接口设计（签名+意图+测试场景）→ 数据流 → 结构变更（先于代码部署）→ 关键代码模板（骨架非全码）→ 文档回写清单。

### 04_tasks.md
依赖图（`Phase0 → [Phase1 ∥ Phase2] → ...`，∥=可并行）→ 任务打勾（每项标完成时间）→ 覆盖矩阵（AC↔测试↔validator）。层名按项目技术栈映射，无对应物删该 Phase。

### 05_validator.md
**可执行验证脚本集，非事后文档**。数据准备 → 验证用例（curl + 预期）→ 数据一致性（上下游链）→ 安全三条件验证 → 合规检查（含资源增减对称）→ 合并后对账（逐 AC 核对证据，防漏适配）→ 审核签字。写码前先读，写完逐节跑，失败→修→重跑（Loop 闭环）。可跑 `scripts/validator-check.sh` 静态检查填充完整性。

### execution-log.md
append-only 事件日志 = **状态事实源**（00_README 状态行仅缓存视图）。粒度：Phase 完成/关键产物/打回更正（微操作不记）。五要素：时间|动作|产物路径+大小|验证方式|状态。并行推进时用 `execution-log/` 目录（一事件一文件防写冲突）。

## 七、与既有体系整合

- **skill 关系**：specs-engine = 方法论；项目自有领域 skill/agent 执行具体动作。发现方法论缺陷 → 改 specs-engine（全局 SSOT）。
- **回溯目录**（如 incidents/、错误案例索引/）：生产问题/踩坑 → 沉淀到项目回溯目录；把坑抽象为 Gate 反哺项目宪法 → 下次自动拦截（举一反三，错只犯一次）。
- **交付检视**：宣称代码完成前对照交付清单（各维度：后端/数据/导入导出/前端等按项目定）逐条查漏，防「代码完成」假象。

## 七-B、会话交接与断点续传（agent 交接，跨会话推进）

> **v2 机械化增强**：本节讲「交接要记什么」（内容层）；机器状态机与续传命令见 [continuity.md](./continuity.md)（`state.json` + `sdd.sh resume`）——两者互补，都读。

> 目的：spec 常跨多会话推进。交接索引 = 接手 agent 恢复上下文的路标，避免「从零重读」或「上下文断在上一手」。

**产出纪律（每个 spec 持续维护）**：
1. **执行期**：execution-log 每关键条目标注来源 session（如 `session: <会话日期-主题>`）。
2. **会话结束/阶段里程碑**：长 spec 产出「断点续传提示词」文件 → 放 spec 目录 `{NN}_断点续传_{YYYYMMDD}.md`（模板见 specs-engine 继续会话提示词模板）；字段含已完成/关键文件/待办。
3. **大阶段完成**：session-record 沉淀到项目记忆区（session-sediment 类 skill 自动做），文件名 `session-record-{日期}-{spec 主题}.md`。
4. **登记交接入口**：specs 索引（README）「交接 Session」列 + 交接索引小节登记锚点——spec 内续传文件给相对链接；memory 的 session-record 记名 + 存放处。
5. **接手 agent 流程**：先查 specs 索引交接列 → 读续传提示词 + execution-log（事实源）→ 恢复上下文再动。

## 八、质量门禁（置 ✅ 前）

```
□ 铁律 Check — 三条铁律无违反
□ 安全三条件 — 退出/幂等/回滚已明确（涉及计费/库存/权限/写操作）
□ 级联影响 — 3 跳调用链/消息消费者已查
□ 测试 — 单元覆盖 + validator 验证通过 + validator-check 无占位符残留
□ execution-log — 与动作同步落账，禁事后回填
□ ✅ 三前置 — 复盘段 + AC 对账 + 澄清状态
```

## 九、时间戳效能（跨项目偏好）

- 必填位置：00_README 变更日志/状态行、tasks 任务完成时间、各文件版本历史。
- 格式 `YYYY-MM-DD HH:MM`，`date` 命令获取；禁编时间/禁丢时分/禁跳号。
- 效能指标：Spec 总耗时 = 最后 task 完成 − 创建；Phase 耗时按首末任务。

## 十、子 Spec（Sub-Spec）

> **本节的正文已拆到 [subspec.md](./subspec.md) —— 只在「父 Spec 下挂子 Spec」时读。**

三条最常用的速记（够判断要不要读全文）：

1. **子 Spec 解决的不是「拆得不够小」，而是「拆了之后共享上下文要重复写 N 份」**。并列兄弟 Spec 拆掉的是共享性；子 Spec 保留共享性、只切分工作量。
2. **四条判据全中才拆**：独立可验收 / 独立边界 / 独立人审 / 可与同类并行或独立排序。**「大」本身不构成理由**——拆分是最后手段（*"Decomposition adds the most overhead of any strategy"*）。
3. **冲突以父为准**；子不建 `laws.md` 与 `execution-log`（继承父）；**父不得先于子关闭**。

骨架与索引用 `scaffold.sh sub` 生成；索引漂移由 `validator-check.sh` 机器对账。

## 十一、长寿命 Spec 的防腐（陈旧检测）

> **为什么有这节**：spec 不是一次性文档。实测（2026-09-01 ~ 10-09 的 2669 条真实会话）显示，主力 spec 的跨度是 **10~11 天、几十次进出**（最长一条 19 天）。用户在同期的原话：
>
> > 「因为这个项目 specs **时间战线拉的太长了，有些内容有些落后的，都需要核实检查对接**」
>
> 业内独立给出同一结论：**"A stale spec is worse than no spec, because everyone trusts it."**
> —— 两份来源指向同一个洞。**没人核实的话，过期的 spec 比没有 spec 更危险**，因为它看起来是权威的。

### 11.1 三条防腐写法（写在源头，不靠事后补救）

| # | 规则 | 为什么 |
|:--:|------|--------|
| 1 | **不写文件路径与行号** | 过期最快。引用代码用 **模块 / 类 / 方法名** —— 名字比位置稳。这与「跨文档引用用章节不用行号」是同一条道理 |
| 2 | **不抄代码片段** | 例外：某段（状态机 / reducer / schema / 类型形状）**比散文更精确地编码了一个决策** —— 这时内联它并注明"来自原型"，**只留决策相关的部分，不是可运行 demo** |
| 3 | **一条事实一个出处** | 每个数字 / 结论带来源（✅ 已实测 / 🟡 文档佐证 / 🔴 仅推断）。**没有出处的陈述 = 下次没人敢信，也没人敢删** |

### 11.2 陈旧信号（命中就标记 + 核实）

**核实不是"重读一遍"，要出去查。** 用户自己给过四类查证源（原话）：

> 「做一下一致性对齐……提示：**可查代码、历史的往期 claude session 会话、相关文档、外部官方的 API 文档**。」

| 存疑类型 | 去哪查 |
|------|------|
| 代码 / 接口现状 | 直接读代码（用名字定位，别用行号） |
| "当时为什么这么定" | 历史的 agent 会话记录 |
| 项目内口径 | 项目现有文档 / 词表 / 台账 |
| 外部事实（版本号 / API / 官方支持周期） | **官方一手文档**（搜索摘要只能找线索，不能当结论） |

> 规模大时（一个 spec 战线拉太长、处处存疑），把这四类查证**当一条独立工作流跑**，而不是边读边猜。

```
□ 某节引用的外部事实（版本号 / 接口 / 客户口径）可能已变，而该节很久没动
□ 一节里出现「待确认 / 待核实 / 临时 / TBD」且已挂超过一周
□ 引用的文件 / 模块已改名或不存在
□ execution-log 体积异常（实测见过单文件 159.9 KB）—— 它本该只记「Phase 完成 / 关键产物 / 打回更正」
□ 状态行还是 🔵，但最后一次实质更新距今很远
```

> **这是复核项（WARN 级），不是硬门禁** —— 硬门禁会让所有老 spec 一起变红，然后所有人学会忽略它（假门禁免疫）。

### 11.3 语义更新，不是堆叠

**改一节时替换它，不要追加一份「更新版在下面」。** 历史由 `execution-log` 与变更日志承载 —— **spec 正文永远只描述当前真相**。

> 判据：一份 spec 读完，读者该拿到的是**现在该怎么想**，不是"这三个月我们怎么想的"。

### 11.4 收口时补一句

置 ✅ 前，在复盘段写明：**这份 spec 的哪些结论是易过期的**（版本号 / 外部口径 / 待确认项），以及"下次什么条件下需要重新核实"。
