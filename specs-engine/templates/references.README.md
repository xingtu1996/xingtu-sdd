# 参考资料索引

> 用途：**跨章节共享的基准材料**放这里。判据——它不是某个 Story/章节专属的，而是**多处以它为真相源**。
> 与 `_work/` 的区别：`_work` 是「结论怎么来的」（过程），`references` 是「结论以什么为准」（基准）。
> 与 `deliverables/` 的区别：`deliverables` 是**给出去的成品**，`references` 是**自己查的底本**，通常不外发。

## 索引

| # | 文件 | 类型 | 服务哪些章节 | 是否已进交付 |
|:--:|---|---|---|:--:|
| 1 | — | — | — | 否 |

**类型枚举**（超出请先问是否该新增）：`术语基线` / `业务规则基线` / `领域模型` / `接口契约` / `数据字典` / `外部标准` / `引用索引`

## 什么该放这里

| 类型 | 例子 | 为什么放这 |
|---|---|---|
| **术语基线** | 统一语言、别名禁令 | 所有章节都要用它定名，改一处影响全篇 |
| **业务规则基线** | R-01…R-23 编号规则表 | 多个 Story 引用同一条规则，各自重写会漂移 |
| **领域模型** | 实体 / 关系 / 状态机 | 架构章、Story 章、测试章都要对照 |
| **接口契约** | 上下游 API/消息体定义 | 属于外部约束，不是本 Spec 发明的 |
| **数据字典** | 字段 → 类型 → 取值 → 出处 | 多处引用，且必须唯一 |
| **外部标准** | 国标 / 行业规范 / 厂商文档 | 引用不复制 |
| **引用索引** | 「哪个事实去哪查」的总表 | 避免每次重新翻找 |

## 不放进这里

| 内容 | 去哪 |
|---|---|
| 过程记录（审查/实测/计划/diff） | `_work/` |
| 用户原话 / 一手材料 | `_prompt/` |
| 对外交付的成品 | `deliverables/` |
| 历史版本 | `_archive/` |
| 本 Spec 自己的结论 | `01~05` 正文 |

## 写法

- **命名带日期**：`{主题}_{YYYYMMDD}.md`（如 `业务规则基线_20261106.md`）
- **文件头写清楚**：生成时间 / 用途 / **谁是真相源**（若本文件只是镜像，必须写明正本在哪）
- **编号要稳**：规则/术语/字段的编号一旦发出就不改号，变化只增不改（`R-01` 永远是 `R-01`）
- **每条带出处**：外部标准标 URL 或文档版本；内部事实标「哪次会议 / 哪封邮件 / 哪次实测」

## 维护判据

| 问题 | 处置 |
|---|---|
| 同一事实在两个 references 文件里说法不一 | 定一个是真相源，另一个改成指针 |
| references 与正文冲突 | **正文错**（Spec is Truth 的推论：基准 > 转述） |
| references 与 `_prompt/` 的原始材料冲突 | **原始材料错不了**——references 是加工件，以 `_prompt/` 一手件为准并修正 references |
| 某文件不再被任何章节引用 | 移入 `_archive/`，注明何时失效 |

## 清理判据

文件超过 20 个时先问：**它还被几个章节引用？**
- ≥2 处 → 留（这就是放这里的理由）
- 只有 1 处 → 应该并进那一处正文，不占 references
- 0 处 → 移 `_archive/`
